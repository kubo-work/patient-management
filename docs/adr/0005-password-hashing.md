# ADR 0005: パスワードを argon2id でハッシュ化し、レスポンスから除去する

- 日付: 2026-09-05
- ステータス: 採用
- 関連: Issue #286 / Epic #279 / ADR 0002 / ADR 0003 / ADR 0004

## 背景

Issue #286 のコメント（2026-08-23）が「認証の作り直しにあたり、パスワードのハッシュ化も本 Issue の範囲に含める必要がある」と定めている。ADR 0004（第 1 フェーズ）はステートレス化のみを扱い、ハッシュ化を含めなかった。本 ADR が第 2 フェーズを扱う。

### 実測した現状

**パスワードは本番・ローカルともに平文で保存されている。** 加えて、着手時に調べたところ **7 つの経路でパスワードがクライアントへ渡っていた**。コメントが指摘していたのは「GET がパスワードを返している」1 点だが、実態はより広い。

| 経路 | 漏洩 | 原因 |
|---|---|---|
| `doctors.list` | あり | `repository/doctors.ts` の `doctorSelect` に `password: true` |
| `doctors.byId` | あり | 同上 |
| `loginDoctor` | あり | 同上（同じ `findDoctorById` を使う） |
| `doctors.create` | あり | `return { data: result }` が Prisma の全カラムを未 parse で返す |
| `doctors.update` | あり | `return await updateDoctor(...)` が同上 |
| `patients.create` | あり | `return await createPatient(...)` が同上 |
| `patients.update` | あり | `return await updatePatient(...)` が同上 |
| `patients.list` | なし | `getPatientsSchema` に `password` が無く zod が除去する |
| `patients.byId` | なし | `patientByIdSelect` に `password` が無い |

漏れていない 2 経路が「zod の出力スキーマに項目が無いから落ちている」だけである点に注意が要る。**除去は意図された設計ではなく、スキーマの副作用として偶然成立している。** 同じ理由で、スキーマに項目を足した瞬間に漏れ始める。

さらに `@repo/schema` の `DoctorType` が `password: string` を必須で宣言しており、型の側からも「パスワードはクライアントに存在する」ことが前提になっている。

### 患者のパスワードには照合経路が存在しない

`appRouter` に患者向けの認証は無い。患者の `password` は生年月日から `YYYYMMDD` で導出され（`domain/patientPassword.ts`）、書き込まれるだけで一度も照合されていない。

### 本番データの移行に使える機会が失われている

コメントは「#282 で Neon へ移行する際にデータ移行が発生するため、そのタイミングで一括ハッシュ化するのが最も無駄がない」としていた。#282 は既に完了しており、この機会は残っていない。

現在の本番は `render-legacy` に固定されており、そのコードは平文照合を行う。本番データをハッシュ化した瞬間に legacy のログインは通らなくなる。**ADR 0004 決定 6（`session` テーブルの削除）とまったく同じ構図**であり、データ移行は #287 の切り替えと同時にしか実行できない。

なおコメントは「`main.yml` は `packages/api/**` の変更で Render デプロイが発火するため、マージした時点で本番へ反映される」と警告しているが、現在の `main.yml` は `workflow_dispatch` のみで、自動デプロイは #280 の時点で停止している。この警告は現状には当てはまらない。

## 決定

### 1. `@node-rs/argon2` による argon2id を採用する

`@node-rs/argon2`（2.2.0、2026-08-29 公開）を `@repo/auth` の依存に加える。パラメータは OWASP の推奨値、すなわち **メモリ 19 MiB・時間コスト 2・並列度 1** を明示的に指定する。ライブラリの既定値に委ねると、版が上がったときにパラメータが黙って変わる。

napi-rs のプリビルドバイナリを使うため `node-gyp` でのコンパイルは走らない。

#### `node:crypto` の `scrypt` を採らなかった理由

当初は依存を増やさない `scrypt` を推していた。退けた理由は 2 つある。

**1. パスワード保存の封筒を自作することになる。** `node:crypto` はプリミティブしか提供せず、ソルトの生成、パラメータの記録、保存フォーマットの設計、`timingSafeEqual` による定時間比較のすべてを自前で書くことになる。argon2 は PHC 形式（`$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`）の自己記述文字列を返し、これらをライブラリ内に閉じ込める。将来パラメータを上げても、古いハッシュはそのハッシュ自身に書かれたパラメータで検証される。

自作した封筒は、正しく書けていても検証コストが高い。`timingSafeEqual` を `===` に書き間違えてもテストは全て通る。

**2. 当初挙げた「コールドスタートへの影響」は誤りだった。** Epic #279 が問題にしている 50 秒のコールドスタートは、Render 無料プランがアイドル時にコンテナごと停止し起こし直す時間である。ネイティブモジュールの読み込みは数ミリ秒のオーダーで、まったく別の現象である。この 2 つを混同していた。ネイティブモジュールの実コストは「Vercel の成果物に linux-x64 用のバイナリが 1 つ載る」ことだけである。

補足として、`scrypt` には OWASP 推奨値（N=2^17, r=8）が `128 × N × r = 128MB` を要求する一方、Node の `scrypt` は既定の `maxmem` が 32MB であるという落とし穴もある。推奨値をそのまま渡すと実行時エラーになる。

`argon2`（npm、0.45.1）は `@node-rs/argon2` と同じ argon2id だが、プリビルドが無い環境では `node-gyp` へフォールバックする。`@node-rs/argon2` を選べる状況で選ぶ理由が無い。

### 2. lazy migration は行わない

新しいコードは argon2 のハッシュのみを検証する。平文を受け付ける分岐を作らない。本番データは #287 の切り替えと同時に一括でハッシュ化する。

この結果、ハッシュ化から Vercel への切り替えまでの間（数分）は legacy のログインが通らない断絶が生じる。これを受け入れる理由は 2 つある。

**1. 断絶の実害が小さい。** 影響は「切り替え作業中の数分間、医師がログインできない」ことだけである。運用者が作業時刻を選べるポートフォリオアプリで、これを避けるために恒久的なリスクを負う理由が無い。

**2. 「あとで消す」は、このリポジトリの実績上、消えない。** #286 の作業だけでも、`apps/web/.env` の `NEXT_DOCTOR_SESSION_SECURE`（express-session 時代の残骸）と、値を書き込むコードが無いまま残っていた `session.destroy()` の 2 つが出てきた。平文を受け付ける分岐が消し忘れられた場合、それは「ハッシュ化したのに平文でもログインできる」という、**ハッシュ化そのものを無効化する穴**になる。しかもテストは通り続ける。

この決定の帰結として、`verifyPassword` は PHC 形式でない文字列（移行漏れの平文など）を渡されたときに **fail-closed** で `false` を返す。`@node-rs/argon2` の `verify` はそうした入力に対して例外を投げるため、これを握って `false` に変換する。移行漏れの行はログインできないのが正しい振る舞いである。

### 3. 患者のパスワードもハッシュ化する

導出ロジック（生年月日から `YYYYMMDD`）は変えず、保存時に argon2 を通す。照合経路が存在しないため、壊れるものが無い。「DB に平文の資格情報が 1 件も無い」という明確な不変条件が立つ。

**この決定の限界を明記しておく。** 推測可能な値（生年月日由来、候補は数万通り）をハッシュ化しても、値そのものの弱さは解消しない。得られるのは「DB が漏れたときに、他サービスへの使い回しが即座に成立しない」ことと「総当たりに 1 アカウントあたりの計算コストが要る」ことだけである。導出ロジック自体の見直しには患者向けの初期パスワード伝達フローが必要で、そのフローは存在しない。別 Issue とする。

#### `patients.password` カラムの削除を採らなかった理由

一度も照合されていない列であり、書き込まれるだけの死んだデータである。使わない資格情報を保持することは純粋な負債であり、削除はエンジニアリングとして正直な選択である。

しかしそれは「患者ログインを実装するのか、しないのか」という製品判断であって、認証のステートレス化を扱う #286 の中で決める話ではない。ハッシュ化は可逆であり、後から削除へ進むこともできる。

### 4. 医師の更新はパスワードを optional にする

`doctors.update` の入力を `password: z.string().optional()` とし、渡されなかった場合はパスワードを変更しない。`doctors.create` は従来どおり必須。

パスワードを返さなくなるため、`useDoctorEdit.ts` が GET の値をフォームへ流し込んで送り返す現在の形（`form.setValues({ password: doctorData.password })`）は成立しない。フォームは常に空で表示し、「変更する場合のみ入力」という位置づけにする。バリデーションは新規作成時のみ必須とする。

#### パスワード変更専用の procedure を採らなかった理由

`doctors.changePassword` を分けると責務が明確になり、将来「現在のパスワードの確認」を足すときの置き場所が自然になる。しかしその要件は現在存在せず、procedure と画面の導線が 1 つ増える。optional 化から専用 procedure への移行は、必要になった時点で局所的に行える。

### 5. ハッシュ化は `@repo/auth` に置き、ログイン照合の時間差を埋める

ADR 0004 で作った `@repo/auth` が認証の共有パッケージであるため、`password.ts` をそこに追加する。`apps/web` はこれを使わない（ハッシュ化は API 側だけの処理である）。

照合の変更にあたり、現行の設計意図を壊さないための追加が要る。現在ログイン失敗のメッセージは「無効なメールアドレスまたはパスワードです。」に統一されており、メールアドレスの存在有無を漏らさない配慮がされている。しかし平文一致（`WHERE email = ? AND password = ?`）をハッシュ照合へ素直に置き換えると、**存在しないメールアドレスは即座に、存在するものは argon2 の計算時間を経て失敗する**ため、応答時間でアカウントの存在が判別できるようになる。メッセージを揃えた意図が時間差で無効化される。

医師が見つからない場合もダミーのハッシュに対して検証を走らせ、応答時間を揃える。

### 6. パスワードをレスポンスから除去する

背景で挙げた 7 経路すべてを塞ぐ。

| 対象 | 変更 |
|---|---|
| `repository/doctors.ts` の `doctorSelect` | `password: true` を削除する |
| `repository/doctors.ts` | ログイン照合専用の `findDoctorByEmail` を追加し、`password` を select するのはここだけにする |
| `repository/doctors.ts` の `updateDoctor` / `createDoctor` | `select: doctorSelect` を指定し、全カラムを返すのをやめる |
| `router/doctors.ts` の `getDoctorSchema` | `password` を外す |
| `router/patients.ts` の `create` / `update` | 戻り値を出力スキーマで parse する |
| `@repo/schema` の `DoctorType` | `password` を削除する |

`DoctorType` から `password` を消すと `useDoctorEdit.ts` が型エラーになる。**これは狙いどおりであり、型が消し忘れを検出する。**

`repository` 側（`select`）と `router` 側（出力スキーマ）の両方で落とすのは冗長に見えるが、意図的である。背景で述べたとおり、現在漏れていない 2 経路は「スキーマに項目が無いから偶然落ちている」状態にある。DB から取り出さないことと、取り出しても返さないことは別の防御であり、片方が破られても他方が残る。

### 7. 移行スクリプトは `packages/api/scripts/` に置き、冪等にする

`packages/api/scripts/hash-existing-passwords.mjs` を新設する。`packages/api` に置くのは、`@repo/db` と `@repo/auth` の両方に既に依存している唯一のパッケージだからである。`packages/db` に置くと db が auth に依存することになり、依存の向きが濁る。

- **冪等**: 値が `$argon2` で始まる行は飛ばす。二重ハッシュ化を構造的に防ぐ。二重ハッシュ化されたアカウントは復旧不能であり、この防御は必須である
- **接続先の明示**: `guarded-migrate.mjs` と同様、localhost 以外への実行は環境変数による明示を要求する
- **対象**: `doctors` と `patients` の両方
- **出力**: 更新件数とスキップ件数のみ。パスワードもハッシュも出力しない

適用のタイミングは決定 2 のとおり、ローカルは即時、本番は #287 の切り替えと同時とする。#287 のチェックリストへ項目を追加する。

### 8. ログインの想定外エラーを 500 にする

Issue のコメントが指摘した 4 点目である。`router/auth.ts` の `catch` が投げる `BAD_REQUEST` を `INTERNAL_SERVER_ERROR` に変える。DB 障害と入力エラーが同じ 400 になり原因を切り分けられない状態を解消する。

なおコメントが問題にしていた「例外オブジェクトをそのまま返して Prisma のエラー詳細が漏れる」点は、#285 の tRPC 化で既に解消している。残っていたのはステータスコードだけである。業務ルールのエラー（未入力・不一致）は現行の `BAD_REQUEST` / `UNAUTHORIZED` のままとし、メッセージも変えない。

## 波及

- **`@node-rs/argon2` のプラットフォーム別バイナリが #287 のリスクになる。** このパッケージは `optionalDependencies` でプラットフォーム別のバイナリを配布する。ローカルは darwin-arm64、Vercel は linux-x64 である。`bun install --frozen-lockfile` が Vercel 上で linux 用のバイナリを解決できるかは **#287 の切り替え時に必ず確認する**。ここが失敗するとログインが動かない
- **レスポンスの形の回帰テストは書けない。** `password` が返らないことを経路ごとに検証するには実 DB が要る。現在の `packages/api` のテストは DB 非依存で成立しており、PGlite は #288 の担当である。本 ADR では `getDoctorSchema` を export し、`password` を持つ行を parse したときに `password` が落ちることの単体テストで代替する。**これは経路全体の保証にはならず、穴として残る**
- **`@repo/auth` が `apps/web` から見て重くなる。** `apps/web` は `@repo/auth` の `verifyDoctorToken` のみを使うが、パッケージのバレル経由で `password.ts` も読み込まれると `@node-rs/argon2` が proxy のバンドルへ入る。`index.ts` からの export を分け、`apps/web` が argon2 を引き込まないようにする
- **ログイン失敗時の応答時間が延びる。** 決定 5 のダミー検証により、存在しないメールアドレスでのログイン失敗も argon2 の計算時間（数十ms）を要するようになる。これは意図した代償である
- **`create` / `update` のレスポンスの形が `password` 以外でも変わる。** 現在これらは Prisma の全カラムを未 parse で返しており、`created_at` / `updated_at` も含まれる。出力スキーマを通すことでこれらも落ちる。`doctors.create` の `{ data: result }` という包みも、他の procedure と揃えて外す。**現在フロントエンドはこれらの戻り値を読んでいない**（`useDoctorEdit.ts` / `usePatientEdit.ts` はいずれも `mutate` の結果を捨てて画面遷移する）ため実害は無いが、tRPC により型が変わるので、読み始めた瞬間にコンパイルエラーとして現れる
- **`derivePatientInitialPassword` の戻り値は保存されなくなる。** 導出した値はハッシュ化されて保存されるため、DB から初期パスワードを読み出すことはできなくなる。現在も患者へ伝達する手段は無いため実害は無いが、患者ログインを実装する際にはこの前提が効いてくる

## スコープ外

いずれも別 Issue として起票する。

- **`doctors.update` に所有者チェックが無い。** ログインしていれば他の医師のパスワードも変更できる。#284 が「トークン無しで任意の医師のパスワードを書き換えられた」穴を塞いだ際、認可は入ったが「自分自身かどうか」の判定は入っていない。意図的な管理者運用なのかどうかの判断が要る
- **患者の初期パスワードが生年月日から推測可能である。** 決定 3 の限界として述べたとおり、修正には患者向けの初期パスワード伝達フローが必要になる
- **ログイン API にレート制限が無い。** ハッシュ化はオフライン攻撃への防御であり、オンラインの総当たりは別の対策を要する

ハッシュ化と認可モデルの変更を同じ差分に乗せると、障害時にどちらが原因か切り分けられなくなる。ADR 0003 が #285 で TanStack Query の導入を退けたのと同じ理由である。
